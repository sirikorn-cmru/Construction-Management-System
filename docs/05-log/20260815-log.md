## 10:20 — SPEC-001 การติดตามโครงการด้วย Earned Value (EVM)

**Requirement ดิบ**: เอกสารเทียบเนื้อหา Chapter 10 (Monitoring and Information Systems) กับระบบ BuildTrack ชี้ว่า Dashboard ปัจจุบันแสดง % ความคืบหน้า และ % งบใช้ไป เป็น 2 ตัวเลขแยกกัน ซึ่งตอบไม่ได้ว่าโครงการคุ้มค่าเงินหรือไม่ ต้องเพิ่ม Earned Value (BCWS/BCWP/ACWP), ดัชนี CPI/SPI, กราฟ EV, Alert Rule Engine และมิติ Quality

**การตัดสินใจ**: NEW — ยังไม่มีเอกสาร spec ใดในระบบ จึงเป็นเอกสารแรก running number 001

**คำถามที่ถามและคำตอบ**:

- ขอบเขตของ SPEC-001 (เอกสารต้นทางพูดหลายเรื่องปนกัน) → **EVM แกนอย่างเดียว** — Alert Rule Engine, มิติ Quality, รูปแบบเก็บข้อมูลอื่น และการเชื่อม Crash Analysis ถูกกันออกไปเป็น spec ฉบับหลัง
- ที่มาของ BCWS ซึ่งเอกสารระบุเองว่าระบบยังไม่มี → **ให้ PM กรอกเองรายงวด** (ไม่ได้เลือกกระจายจาก S-curve หรือล็อกงบต่องานใน WBS)
- ความถี่ในการคำนวณและเก็บค่า → **คำนวณสด + snapshot รายสัปดาห์**
- โครงการนี้คือระบบ BuildTrack หรือไม่ → **ใช่ เป็นระบบเดียวกัน** spec จึงอ้างโมดูล Dashboard/Daily Report/Payment/Issues ว่ามีอยู่แล้ว

**ข้อสมมติที่ตั้งไว้**:

- BCWP คำนวณจาก % ความคืบหน้า **รวมทั้งโครงการ** × งบรวม เพราะยังไม่มีงบประมาณแยกรายงานใน WBS — เป็นค่าที่หยาบกว่าหลักตำรา
- งวดของ BCWS ใช้รอบเดียวกับ snapshot คือรายสัปดาห์
- ตัวเลขในเกณฑ์การยอมรับข้อ 1 (68%, 50M, 21M, 30M) เป็นตัวอย่างสมมติจากเอกสารต้นทาง ไม่ใช่ข้อมูลจริง

**ความเสี่ยงที่รับไว้อย่างรู้ตัว**: การให้ PM กรอก BCWS เองแปลว่า baseline ไม่ถูกล็อก ขัดกับหลักในตำราที่ว่า baseline ต้องไม่แก้ย้อนหลัง เปิดช่องให้ปรับ BCWS จนตัวเลข SV/SPI ดูดีได้ บรรเทาด้วยกฎ append-only (BR-001-04) และหน้าประวัติการแก้ไข (FR-001-11) เมื่อ WBS มีงบต่องานแล้วควรออก spec ใหม่เปลี่ยนที่มาของ BCWS

**คำถามที่ยังค้าง**: งวดรายสัปดาห์เริ่มนับวันไหน, ใครมีสิทธิ์แก้ BCWS นอกจาก PM, ระบบควรทำอะไรถ้า PM ไม่กรอก BCWS ติดต่อกันหลายงวด

## 10:30 — แก้ SPEC-001: BCWS เป็น baseline ที่ล็อกแล้ว

**สิ่งที่เปลี่ยน**: ผู้ใช้กลับคำตัดสินใจเรื่องที่มาของ BCWS จาก "PM กรอกเองรายงวดระหว่างดำเนินงาน แก้ได้พร้อมเหตุผล" เป็น **"ล็อกไว้ตอนวางแผนและไม่แก้ย้อนหลัง"** ซึ่งตรงกับหลักในตำราที่เอกสารต้นทางอ้างถึง

**เหตุผล**: การให้แก้ BCWS ระหว่างทางเปิดช่องให้ปรับตัวเลขจน SV/SPI ดูดี ซึ่งทำลายจุดประสงค์ของ EVM ทั้งหมด — ความเสี่ยงข้อนี้ถูกบันทึกไว้ในรอบก่อนหน้าและตอนนี้ถูกปิดด้วยการเปลี่ยนกฎ

**ผลต่อ spec**:

- FR แยกเป็น 3 กลุ่ม (Baseline / การคำนวณ / การแสดงผล) และเพิ่มจาก 12 เป็น 15 ข้อ เลข FR เดิมถูกเรียงใหม่ทั้งหมด
- เพิ่ม FR-001-02 ปฏิเสธการแก้ไข baseline ทุกกรณี และ FR-001-03/04 กลไก **re-baseline แบบมีเวอร์ชัน** — ต้องมีเหตุผล ผู้อนุมัติ วันที่มีผล ครบทั้ง 3 อย่าง และเวอร์ชันเดิมเก็บไว้ครบ
- BR-001-01 ถึง BR-001-03 เป็นกฎชุดใหม่เรื่องการล็อกและการคิดดัชนีตามเวอร์ชัน baseline ที่มีผล ณ งวดนั้น — re-baseline จะไม่เปลี่ยนตัวเลขของงวดที่ผ่านมาแล้ว
- เพิ่ม NFR ว่าการล็อกต้องบังคับที่ชั้นฐานข้อมูล ไม่ใช่แค่ชั้นหน้าจอ
- FR-001-13 เปลี่ยนจาก "รอข้อมูล BCWS" รายงวด เป็น "ยังไม่ได้ตั้ง baseline" ระดับโครงการ เพราะ baseline ถูกกรอกครบทุกงวดตั้งแต่ต้น
- หัวข้อ "ความเสี่ยงที่รับไว้อย่างรู้ตัว" ถูกแทนด้วย "ข้อจำกัดที่รู้ตัว" — ที่เหลืออยู่คือความ*แม่นยำ*ขึ้นกับคุณภาพการวางแผน แต่ความ*น่าเชื่อถือ*ไม่ได้ลดลงแล้ว
- คำถามค้างเปลี่ยน 2 ข้อ: ตัดเรื่องสิทธิ์แก้ BCWS และ PM ไม่กรอกติดกันหลายงวดออก เพิ่มเรื่องผู้อนุมัติ re-baseline และการแสดงเส้น baseline เดิมบนกราฟ

**การตัดสินใจที่ผมทำเองในรอบนี้**: อนุญาตให้ **re-baseline แบบมีเวอร์ชัน** ได้ เพราะงานก่อสร้างมี change order เป็นเรื่องปกติ การห้ามเปลี่ยนแผนโดยสิ้นเชิงจะทำให้ดัชนีไร้ความหมายเมื่อขอบเขตงานเปลี่ยนจริง กลไกนี้ไม่ใช่การ "แก้ย้อนหลัง" เพราะเวอร์ชันเดิมยังอยู่ครบและตัวเลขของงวดที่ผ่านมาไม่เปลี่ยน — ถ้าต้องการห้ามเปลี่ยนเด็ดขาดจริง ๆ ต้องแจ้งเพื่อตัด FR-001-03/04 ออก

**ผลต่อ backlog**: แก้เลข FR ที่อ้างถึงในทุกแถว ปรับข้อความ BL-001-02, BL-001-10, BL-001-11 และเพิ่ม BL-001-13 ถึง BL-001-17 (baseline table แบบมีเวอร์ชัน, บังคับ immutability ที่ DB, หน้า re-baseline, คิดดัชนีตามเวอร์ชัน, แสดงเวอร์ชันบน Dashboard) รวมเป็น 17 รายการ

## 10:37 — ปิดคำถามค้างทั้ง 3 ข้อของ SPEC-001

**คำถามที่ถามและคำตอบ**:

- งวดรายสัปดาห์เริ่มนับวันไหน → **ทุกวันจันทร์** (ไม่เลือกนับจากวันเริ่มโครงการ หรือตัดตามรอบเบิกจ่าย) เหตุผลคืองวดตรงกันทุกโครงการ เทียบข้ามโครงการได้ และงาน snapshot อัตโนมัติเขียนง่าย
- ใครอนุมัติ re-baseline → **ผู้บริหาร 1 คน** (ไม่เลือกอนุมัติ 2 ระดับ หรือผูกกับ change order ที่อนุมัติแล้ว) เหตุผลคือเหมาะกับขนาดทีมปัจจุบันและกันการเปลี่ยนแผนพร่ำเพรื่อได้พอสมควร
- EV Chart แสดงเส้น baseline เก่าอย่างไร → **เส้นเก่าจาง + เส้นปัจจุบันทึบ** (ไม่เลือกแสดงเฉพาะเวอร์ชันปัจจุบัน หรือให้ผู้ใช้สลับเปิดปิดเอง) เหตุผลคือเห็นในภาพเดียวว่าแผนถูกเลื่อนไปเท่าไร

**ผลต่อ spec**: แปลงคำตอบเป็นกฎ 3 ข้อ — BR-001-08 นิยามงวด, BR-001-09 ผู้อนุมัติ, BR-001-10 การแสดงเส้น baseline เก่า เพิ่ม FR-001-16 (เส้นจาง/เส้นทึบ) แก้ FR-001-03 ให้ระบุว่าผู้บริหารเป็นผู้อนุมัติ และเพิ่มเกณฑ์การยอมรับข้อ 7–9 หัวข้อ "คำถามที่ยังค้าง" เปลี่ยนเป็น "ไม่มีคำถามค้าง"

**การตัดสินใจที่ผมทำเองในรอบนี้** — เป็นรายละเอียดที่ตามมาจากคำตอบข้างต้นโดยตรง จึงไม่ได้ถามซ้ำ แต่บันทึกไว้ให้ตรวจสอบได้:

- งวดแรกและงวดสุดท้ายที่ไม่ครบ 7 วัน นับเป็นหนึ่งงวดเต็ม ไม่เฉลี่ยตามสัดส่วนวัน — ทางเลือกอื่นคือเฉลี่ย BCWS ตามจำนวนวันจริง ซึ่งแม่นกว่าแต่ทำให้กราฟงวดแรกดูผิดปกติ
- จำกัดเส้น baseline เก่าบนกราฟไว้ 2 เวอร์ชันล่าสุด ส่วนที่เกินดูในหน้าประวัติ — ถ้าไม่จำกัด กราฟจะอ่านไม่ออกเมื่อ re-baseline หลายครั้ง
- ผู้ยื่นคำขอ re-baseline อนุมัติคำขอตนเองไม่ได้ แม้มีสิทธิ์ระดับผู้บริหาร — เพราะถ้าอนุมัติเองจบ กลไกการล็อก baseline ก็ไม่มีผลอะไรเลย

**ผลต่อ backlog**: เพิ่ม BL-001-18 ถึง BL-001-20 (นิยามงวดจันทร์–อาทิตย์, สิทธิ์อนุมัติ re-baseline, เส้น baseline เก่าบนกราฟ) รวมเป็น 20 รายการ ครั้งนี้เพิ่มแถวใหม่อย่างเดียวตามกฎ append-only ไม่ได้แก้แถวเดิม

## 10:44 — SPEC-002 Alert Rule Engine ปิด Loop จาก Monitor สู่ Control

**Requirement ดิบ**: หัวข้อ Planning-Monitoring-Controlling Loop ในเอกสารเทียบ Chapter 10 ซึ่งชี้ว่า BuildTrack ทำได้ถึงแค่ "Monitor" แต่ไม่มีขั้น "Control" — เสนอให้ผูก CPI/SPI เข้ากับ Notification และสร้าง Issue อัตโนมัติในโมดูล Issues ที่มีอยู่แล้ว หัวข้อนี้ถูกกันออกจากขอบเขตของ SPEC-001 ไว้ตั้งแต่ต้น

**การตัดสินใจ**: NEW — คนละเรื่องกับ SPEC-001 ชัดเจน SPEC-001 คือการ *วัด* SPEC-002 คือการ *ทำอะไรกับสิ่งที่วัดได้* และ SPEC-001 ระบุไว้เองว่าไม่ครอบคลุมส่วนนี้ จึงไม่ทับซ้อน แต่ SPEC-002 พึ่งพา SPEC-001 โดยตรง จึงเพิ่มหัวข้อ "เอกสารที่ต้องมีก่อน" ระบุ 5 จุดที่พึ่งพา

**คำถามที่ถามและคำตอบ**:

- Alert Rule Engine ควรยืดหยุ่นแค่ไหน → **เฉพาะ CPI/SPI เกณฑ์ตายตัว** (ไม่เลือกให้ตั้งกฎเองบนตัวชี้วัด EVM หรือทำ engine ทั่วไปทุกตัวชี้วัด) การเปลี่ยนเกณฑ์ต้องแก้โค้ด
- เมื่อกฎถูก trigger ระบบทำอะไร → **สร้าง Issue อัตโนมัติ + แจ้งเตือน** (ไม่เลือกแจ้งเตือนอย่างเดียว หรือสร้างเป็นร่างรออนุมัติ) ตรงกับที่ตำราเน้นว่าต้องปิด loop
- กันการแจ้งซ้ำอย่างไร → **1 Issue ต่อกฎ ตราบที่ใบเดิมยังไม่ปิด** งวดถัดมาที่ยังเข้าเงื่อนไขให้เพิ่ม comment แทน (ไม่เลือกสร้างใหม่ทุกงวด หรือสร้างใหม่เมื่อข้ามระดับสี)
- ช่องทางแจ้งเตือน → **ในระบบอย่างเดียว** อีเมลและ LINE ถูกกันออกจากขอบเขต

**การตัดสินใจที่ผมทำเองในรอบนี้** — ตามมาจากคำตอบข้างต้นโดยตรง:

- ประเมินกฎเฉพาะหลังบันทึก snapshot รายสัปดาห์ ไม่ประเมินตอนเปิด Dashboard (BR-002-02) เพราะ SPEC-001 ให้คำนวณสดทุกครั้งที่เปิดหน้า ถ้าประเมินกฎด้วยจะยิงแจ้งเตือนทุกครั้งที่มีคนเปิดดู
- ระดับเหลืองแจ้งเตือนอย่างเดียว ไม่สร้าง Issue (BR-002-06) เพราะระดับเฝ้าระวังยังไม่ใช่ปัญหาที่ต้องมีคนรับผิดชอบ
- ไม่ปิด Issue อัตโนมัติเมื่อค่ากลับมาดี (BR-002-04) เพราะตัวเลขกลับมาดีไม่ได้แปลว่ามีใครแก้อะไร อาจเป็นความผันผวนของงวด การปิดเองจะลบหลักฐานว่าเคยมีปัญหา
- ข้อความ Issue และการแจ้งเตือนต้องอ่านรู้เรื่องโดยไม่ต้องรู้ศัพท์ EVM เพราะผู้รับคือผู้บริหาร

**เนื้อหา spec**: 16 FR แบ่ง 4 กลุ่ม (กฎและการประเมิน / การสร้าง Issue / การแจ้งเตือน / การตรวจสอบย้อนหลัง), 6 BR, 3 NFR, 8 เกณฑ์การยอมรับ

**คำถามที่ยังค้าง 3 ข้อ**: CPI และ SPI ต่ำพร้อมกันควรได้ Issue 2 ใบหรือ 1 ใบรวม, นิยาม "ผู้บริหารที่เกี่ยวข้องกับโครงการ", และควรประเมินกฎต่อหรือไม่เมื่อโครงการปิดหรือพักงาน

**ผลต่อ backlog**: เพิ่ม BL-002-01 ถึง BL-002-17 รวม backlog ทั้งหมดเป็น 37 รายการ

## 10:55 — เพิ่มสกิลตรวจสอบความสอดคล้อง backlog กับ spec

## 11:02 — สร้างกระบวนการอนุมัติ spec

**คำถามที่ถามและคำตอบ**:

- ใครเป็นผู้อนุมัติ → **เจ้าของโปรเจกต์คนเดียว** (ไม่เลือกให้มีผู้ตรวจก่อน หรือระบุผู้อนุมัติต่อ spec)
- spec ที่ approved แล้วแก้ได้แค่ไหน → **แก้ถ้อยคำได้ แต่แก้เนื้อหาต้อง supersede** (ไม่เลือกห้ามแก้ทุกกรณี หรือแก้ได้ทุกอย่างแล้วเพิ่มเลขรุ่น)
- เริ่มทำ backlog จาก spec ที่ยัง draft ได้หรือไม่ → **ทำได้ แต่ต้องทำเครื่องหมายไว้**
- เงื่อนไขก่อนอนุมัติ → **ไม่มีคำถามค้าง + ทุก FR มี backlog รองรับ + ผ่าน audit**

**สิ่งที่สร้าง**:

- subagent `spec-readiness-reviewer` — ตรวจ 5 gate ของ spec หนึ่งฉบับ: คำถามค้าง, FR coverage, ข้อสมมติที่ระบุที่มาได้, dependency ข้าม spec, ความครบถ้วนภายใน คืนผล PASS/FAIL พร้อมหลักฐาน และสรุปให้ผู้อนุมัติอ่านโดยไม่ต้องอ่านทั้งฉบับ
- สกิล `approve-spec` — 8 ขั้นตอน ตรวจสถานะปัจจุบัน รัน gate ด้วย 2 subagent พร้อมกัน (readiness + backlog audit) เสนอผลให้เจ้าของตัดสิน แล้วจึงเปลี่ยนสถานะ อัปเดต index ล้างเครื่องหมาย (draft) ใน backlog และบันทึก log

**หลักการที่บังคับไว้**: **สกิลไม่อนุมัติเอง** gate ที่ผ่านไม่ใช่การอนุมัติ ต้องมีคำตอบชัดเจนจากเจ้าของโปรเจกต์ในบทสนทนาเท่านั้น และการอนุมัติที่ถูกปฏิเสธหรือเลื่อนออกไปก็ต้องบันทึก log เหมือนกัน เพราะเหตุผลที่ไม่อนุมัติมีค่าเท่ากับเหตุผลที่อนุมัติ

**ผลกระทบต่อกระบวนการเดิม**:

- `requirement-analyst` — ตัวเลือก EXTEND ใช้ได้เฉพาะกับ spec ที่ยังเป็น draft เท่านั้น ถ้าเป้าหมายเป็น approved และการเปลี่ยนแปลงแตะ FR/BR/ขอบเขต/เกณฑ์การยอมรับ ต้องเป็น SUPERSEDE และให้รายงานสถานะของ spec เป้าหมายมาด้วยเสมอ
- `requirement-to-backlog` — เขียนคอลัมน์ Spec เป็น `SPEC-{NNN} (draft)` ระหว่างที่ spec ยังไม่อนุมัติ
- `backlog-auditor` — เพิ่มการตรวจว่าเครื่องหมาย (draft) ตรงกับสถานะจริงของ spec ทั้งกรณีขาดและกรณีค้างอยู่ทั้งที่อนุมัติแล้ว

**ผลต่อ backlog**: เติมเครื่องหมาย `(draft)` ให้ทั้ง 40 รายการ เพราะ SPEC-001 และ SPEC-002 ยังเป็น draft ทั้งคู่ และเพิ่มคำอธิบายเครื่องหมายในหัวตาราง ตอนนี้ทุกแถวมีเครื่องหมายเหมือนกันหมดจึงยังไม่มีประโยชน์ แต่จะเริ่มมีความหมายทันทีที่ spec ฉบับแรกได้รับอนุมัติ

## 21:02 — SPEC-003 สถาปัตยกรรมฟังก์ชันของระบบบริหารโครงการก่อสร้าง

**Requirement ดิบ**: โจทย์ให้ออกแบบสถาปัตยกรรมฟังก์ชันของระบบบริหารโครงการก่อสร้าง แบ่งเป็น User Journey ของลูกค้า / Core Feature List (Customer-facing + "Barista Display System") / Data Entities หลัก ผลการออกแบบที่ตอบกลับในบทสนทนาถูกนำมาแปลงเป็น spec ฉบับนี้

**การตัดสินใจ**: NEW — หัวเรื่องคือสถาปัตยกรรมของทั้งระบบ คนละ subject กับ SPEC-001 (การคำนวณ EVM) และ SPEC-002 (กฎเตือน) ซึ่งเป็นฟีเจอร์ย่อยในกลุ่ม PM & Executive Console ของสถาปัตยกรรมนี้

**จุดชนที่ subagent จับได้และต้องตัดสินก่อนเขียน**: การออกแบบกำหนดเส้นทาง `WBS_Task.งบต่องาน → BCWS` และ `Progress_Update.% ต่องาน → BCWP` ซึ่งขัดกับ BR-001-04 / FR-001-05 และข้อสมมติ A2/A5 ของ SPEC-001 ที่ใช้ % รวมทั้งโครงการ × งบรวม ถ้าเลือกเปลี่ยนแกนจริง SPEC-003 ต้องเป็น SUPERSEDE ไม่ใช่ NEW

**คำถามที่ถามและคำตอบ** (ถาม 6 ข้อ ตัดคำถามเรื่องที่มาของ ACWP ออกเพราะ FR-001-06 ของ SPEC-001 ตอบไว้แล้ว บันทึกเป็นข้อสมมติ A4 แทน):

- รูปร่างของ SPEC-003 → **umbrella spec** กำหนดขอบเขต กลุ่มผู้ใช้ แบบจำลองข้อมูล และกฎข้ามโมดูล แล้วแตก spec ลูกทีหลัง (ไม่เลือกเขียนฉบับเดียวจบ ~40 FR หรือแตกเป็น 3 spec ทันที)
- จุดชนแกน EVM → **เก็บโครงสร้าง WBS ที่มีงบต่องานไว้ แต่การคำนวณยังตาม SPEC-001** จนกว่าจะมี spec ใหม่ที่ supersede (ไม่เลือก supersede ทันที หรือแยก spec เฉพาะกิจ) เหตุผลคือ BL-001-01..20 ยัง "ยังไม่เริ่ม" ทั้งหมด การ supersede ตอนนี้จ่ายราคาเอกสารเต็มโดยยังไม่ได้ประโยชน์
- หน่วยวัดความคืบหน้าหน้างาน → **rule of credit 0/50/100** (ไม่เลือกกรอก % อิสระ หรือเทียบ BOQ) เพราะเป็น input เดียวของ BCWP และหน้างานต้องกดด้วยถุงมือกลางแดด
- กลไกกฎการมองเห็นข้อมูลของลูกค้า → **กำหนดตายตัวรายชนิดข้อมูล + ธงเปิดเผยราย record สำหรับ Issue และเอกสาร**
- ตัวเลขผลกระทบ Change Order → **สองขั้น** ลูกค้ายื่น PM ประเมินตอบเป็นตัวเลขผูกพัน ลูกค้ายืนยัน (ไม่เลือกประเมินอัตโนมัติทันที หรือแสดงช่วงประมาณการก่อน)
- ขอบเขตออฟไลน์ → **อ่านจาก cache + เขียนลงคิว ชนกันให้คนตัดสิน** ห้าม last-write-wins

**การตัดสินใจที่ผมทำเองในรอบนี้**:

- แบบก่อสร้างที่ cache ไว้ขณะออฟไลน์ **เปิดได้แต่ต้องเตือนพร้อมเวลา sync ล่าสุด** ไม่บล็อก เพราะการบล็อกทำให้ทำงานออฟไลน์ไม่ได้จริง ซึ่งขัดกับเหตุผลทั้งหมดที่มีชั้นออฟไลน์อยู่
- ธง "เปิดเผยต่อลูกค้า" ใช้กับทั้ง `Issue` และ `Document` ไม่ใช่เฉพาะ Issue เพราะเอกสารภายในมีปัญหาแบบเดียวกัน

**เนื้อหา spec**: 18 FR แบ่ง 6 กลุ่ม, 10 BR, 3 NFR, 10 เกณฑ์การยอมรับ, ตาราง Entity 19 รายการ พร้อมภาคผนวก ก ที่เป็นบัญชีฟีเจอร์ CF-01..13, SD-01..12 และ PM-01..08 ให้ spec ลูกอ้างอิงกลับได้ — BR-003-09 บันทึกไว้ชัดว่าการคำนวณ EVM ยังเป็นของ SPEC-001

**finding รอบ 21:21 ปิดจริงทั้ง 9 ข้อ** — auditor ตรวจยืนยันทีละข้อ: F1 (FR-003-02 ใช้ BR-003-12/13 ของตัวเองแล้ว), F2 (BL-003-22), F3 (BL-002-14/15 อ้างรหัส NFR จริง), F4 (BR-003-09 แยก BCWP/BCWS + แผนภาพใหม่ + BL-003-29), F5 (FR-003-17 + BR-003-14/15 + BL-003-25/26/27), F6 (A5 + FR-003-21 + BL-003-28), F7, F9, F10 เหลือ F8 ที่ค้างและถูกรายงานซ้ำเป็น F6 ของรอบนี้ นอกจากนี้ไม่มี dangling reference ไม่มี id ซ้ำหรือขาด และทุกแถวมีเครื่องหมาย `(draft)` ครบ

**ข้อสังเกตของรอบนี้**: finding ใหม่เกือบทั้งหมดเกิดจากการเติมรหัส NFR เมื่อ 21:45 — พอ NFR มีรหัส การตรวจ coverage จึงมองเห็นว่าหลายข้อไม่มีใครคุม ซึ่งเป็นสิ่งที่ตั้งใจให้เกิด การเติมรหัสจึงคุ้มค่าทันทีในรอบเดียว

**สิ่งที่แก้ใน backlog**:

- **F1 [BLOCKER]** เพิ่ม BL-001-22 — NFR-001-01 (คำนวณสดทุกครั้งที่เปิด Dashboard) ไม่มีแถวคุม ถ้าปล่อยไว้ผู้ทำ BL-001-06 มีอิสระที่จะอ่านค่าจาก snapshot งวดล่าสุดแทน ผู้บริหารจะเห็นตัวเลขเก่าได้ถึง 6 วัน และเหตุผลของ BR-002-02 ที่อ้างพฤติกรรมคำนวณสดจะลอยทั้งข้อ
- **F2** เพิ่ม BL-003-30 — NFR-003-01 (ปุ่มใหญ่ กลางแดด ถุงมือ) ไม่มีแถวคุม เสี่ยงตกหล่นตรงรอยต่อระหว่าง umbrella กับ spec ลูก ทั้งที่เป็นเหตุผลตั้งต้นของส่วนงานหน้างานทั้งหมด
- **F3** เพิ่ม BL-003-31 (`Payment_Request`) และยกระดับ BL-002-17 เป็น Must พร้อมระบุว่าสร้าง entity `Alert_Event` — สอง entity สุดท้ายในข้อ 8 ที่ FR-003-03 (Must) บังคับแต่ยังไม่มีแถวคุมในระดับเดียวกัน
- **F4** แก้ข้อความ BL-001-13, BL-001-14, BL-001-15, BL-001-16, BL-001-17 ให้เรียก entity ว่า `Schedule_Baseline` ตามข้อ 8 — อาการเดียวกับ F10 รอบก่อนที่แก้ให้ BL-001-01 ใช้ `EV_Snapshot` แต่ตกชุด baseline ไป ถ้าไม่แก้จะจบด้วย baseline สองชุดที่ BR-001-03 กับ BR-003-15 อ้างคนละใบ
- **F5 (ส่วน backlog)** แก้ข้อความ BL-003-07 ให้ระบุข้อยกเว้นของผู้บริหารตาม BR-003-12 — กันไม่ให้คนทำแถวนี้สร้าง guard ที่ปฏิเสธผู้บริหารทุกกรณีแล้วต้องรื้อซ้ำตอนทำ BL-003-23

- **F7** เติมรหัส NFR ในคอลัมน์อ้างอิงของ BL-001-09, BL-001-14, BL-003-03, BL-003-08 ซึ่งเนื้อหาคุม NFR อยู่แล้วแต่ยังอ้างเฉพาะ FR

**คำถามที่ถามและคำตอบ**:

- ความสำคัญของ BL-002-17 → **ยกระดับเป็น Must** ให้ตรงกับ FR-003-03 ที่บังคับให้มี `Alert_Event`

- ข้อสมมติ A2 ของ SPEC-002 (มี in-app notification อยู่แล้วหรือไม่) → **ยังไม่มี ต้องสร้างใหม่**

**สิ่งที่ไม่ได้แก้และเหตุผล** — ต้องแก้ที่ spec ซึ่งอยู่นอกอำนาจของสกิลนี้ คำตอบได้ครบแล้ว รอทำผ่าน `requirement-to-backlog` แบบ EXTEND:

1. **เกณฑ์การยอมรับข้อ 10 ของ SPEC-003** ต้องเติม "ยกเว้นกรณีตามข้อ 11–12" ไม่งั้นเกณฑ์ข้อ 10 กับข้อ 11–12 ขัดกันเองในเอกสารเดียวกัน
2. **ข้อสมมติ A2 ของ SPEC-002** ต้องแก้จาก "มีอยู่แล้ว *หรือสร้างขึ้นใหม่ได้*" เป็น "ยังไม่มี ต้องสร้างใหม่ในขอบเขตนี้" และเปลี่ยนที่มาเป็นยืนยันโดยผู้ใช้
3. **ข้อสมมติที่ที่มาเป็น "ตัดสินใจในรอบนี้" และหัวข้อ "การตัดสินใจที่ทำแทนโดยไม่ได้ถาม" ทั้ง 3 สเปค** ต้องเปลี่ยนที่มาเป็น "ยืนยันโดยผู้ใช้ 2026-08-15" — ผู้ใช้ยืนยันทั้งชุดแล้ว นี่คือ gate 3 ของ `approve-spec` ที่จะติดอยู่ดีถ้าไม่ทำ

**ผลต่อ backlog**: เพิ่ม 4 แถว (BL-001-22, BL-002-21, BL-003-30, BL-003-31) รวมทั้งหมด 74 รายการ แก้ข้อความ 6 แถว แก้อ้างอิง 4 แถว ยกระดับความสำคัญ 1 แถว

## 22:13 — แก้ 3 เรื่องค้างจาก audit รอบ 2 และยืนยันข้อสมมติทั้ง 3 สเปค

**Requirement ดิบ**: แก้ 3 เรื่องที่ `audit-backlog` รอบ 21:58 พบแต่แก้ไม่ได้เพราะอยู่ในตัว spec — เกณฑ์การยอมรับข้อ 10 ของ SPEC-003 ขัดกับข้อ 11–12, ข้อสมมติ A2 ของ SPEC-002 ต้องแก้เป็น "ยังไม่มี ต้องสร้างใหม่", และข้อสมมติที่ที่มาเป็น "ตัดสินใจในรอบนี้" ทั้ง 3 สเปคต้องเปลี่ยนเป็น "ยืนยันโดยผู้ใช้"

**การตัดสินใจ**: EXTEND ทั้ง 3 ไฟล์ — ไม่ได้เพิ่มหัวข้อใหม่ให้ระบบ แต่แก้ความขัดแย้งภายในเอกสารเดิมและบันทึกที่มาของข้อสมมติที่ผู้ใช้ยืนยันแล้ว ทุกฉบับยัง `draft` จึงยังไม่เข้าเงื่อนไข supersede

**คำถามที่ถามและคำตอบ**:

- วิธีแก้ → **EXTEND ทั้ง 3 สเปคในที่** (ไม่เลือกออก SPEC-004 ที่ supersede หรือแก้เฉพาะ SPEC-003)
- ขอบเขตกลไกแจ้งเตือนที่ต้องสร้าง → **เท่าที่ FR-002-13/14/15 ต้องใช้** (ไม่เลือก Notification Center เต็มรูป หรือแพลตฟอร์มเหตุการณ์กลาง) เหตุผลคือปัญหาที่ audit จับได้คือ "งานสร้าง subsystem หลุดจากการประเมิน" ไม่ใช่ "กลไกยังไม่ดีพอ"
- FR ของงานสร้างกลไก → **เพิ่ม FR-002-18** (ไม่เลือกให้ BL-002-21 อ้าง FR-002-13 ต่อ หรือแยกเป็น SPEC-004) เพราะ FR-002-13 กำลังแบกความหมายสองชั้นคือ "สร้างกลไก" กับ "กำหนดผู้รับ" ซึ่งเป็นต้นเหตุเดียวกับที่ทำให้งานหลุดรอบแรก
- รูปแบบการบันทึกการยืนยัน → **เปลี่ยนชื่อหัวข้อเป็น "การตัดสินใจที่ผู้ใช้ยืนยันแล้ว (2026-08-15)"** ตัดประโยค "ถ้าไม่ตรงกับที่ต้องการให้แจ้ง" ออก และคง bullet พร้อมเหตุผลไว้ครบ (ไม่เลือกเติมบรรทัดนำในหัวข้อเดิม หรือยกทุก bullet ขึ้นตารางข้อสมมติ)
- ความขัดกันเรื่องงบต่องานใน WBS → **แก้เหตุผลของ A2/A5 ให้ตรงกับ BR-003-09** (analyst พบเพิ่มเอง)
- A5 ของ SPEC-003 อ้างช่องทางที่ยังไม่มีอยู่จริง → **เติมใน A5 + เพิ่มความพึ่งพาในตารางข้อ 3** (analyst พบเพิ่มเอง)

**สิ่งที่เปลี่ยน**:

- **SPEC-003** — เกณฑ์การยอมรับข้อ 10 เติมข้อยกเว้นอ้าง BR-003-12/13 และชี้ไปข้อ 11–12 (ข้อ 10 กลายเป็นกฎตั้งต้น ไม่ขัดกับข้อยกเว้นอีก), A6 เปลี่ยนที่มาเป็นยืนยันโดยผู้ใช้, A5 เติมว่าช่องทาง in-app ยังไม่มีต้องสร้างตาม FR-002-18 ก่อน, ตารางข้อ 3 ระบุความพึ่งพานี้, เปลี่ยนชื่อหัวข้อการตัดสินใจ
- **SPEC-002** — A2 เปลี่ยนเป็น "ยังไม่มี ต้องสร้างใหม่" ตัดถ้อยคำ "หรือสร้างขึ้นใหม่ได้" ที่เป็นช่องให้งานหลุด, เพิ่ม FR-002-18 เป็นฐานของ FR-002-13 ถึง 15, เขียนขอบเขตของกลไกที่ต้องสร้างลงหัวข้ออยู่ในขอบเขต และระบุความสามารถที่เกินกว่านั้น (สถานะอ่าน ตัวนับ ตั้งค่ารายผู้ใช้) ไว้นอกขอบเขต, เปลี่ยนชื่อหัวข้อการตัดสินใจ
- **SPEC-001** — A2/A5 เปลี่ยนที่มาเป็นยืนยันโดยผู้ใช้ พร้อมแก้เหตุผลจาก "WBS ยังไม่มีงบต่องาน" เป็น "มีงบต่องานแล้วแต่รอบนี้ยังไม่ป้อนเข้า EVM ตาม BR-003-09" ซึ่งลบความขัดกับ FR-003-04 ไปด้วย, แก้ย่อหน้าข้อจำกัดที่รู้ตัวให้ตรงกัน, ยกรายการตัดสินใจแทน 3 ข้อขึ้นเป็นหัวข้อของตัวเองให้โครงสร้างตรงกับอีก 2 ฉบับ

**ผลต่อ backlog**: ไม่มีแถวใหม่ — แก้เฉพาะช่องอ้างอิงของ BL-002-21 จาก FR-002-13 เป็น FR-002-18 และขยายข้อความให้ระบุขอบเขต รวมยังคง 74 รายการ

**สถานะ**: ทั้ง 3 สเปคยังเป็น `draft` — การยืนยันข้อสมมติไม่ใช่การอนุมัติ spec การเปลี่ยนเป็น `approved` ต้องผ่าน `approve-spec` แยก ตอนนี้ gate 3 (ข้อสมมติระบุที่มาได้ทุกข้อ) ควรผ่านแล้วทั้ง 3 ฉบับ

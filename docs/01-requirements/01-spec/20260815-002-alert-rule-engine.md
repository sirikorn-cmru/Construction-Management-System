# SPEC-002 — Alert Rule Engine ปิด Loop จาก Monitor สู่ Control

## 1. ที่มาและวัตถุประสงค์

ที่มาจากเอกสารเทียบเนื้อหา Chapter 10 กับระบบ BuildTrack หัวข้อ Planning-Monitoring-Controlling Loop:

> **ปัจจุบัน BuildTrack ทำได้ถึงแค่ "Monitor"** (Dashboard แสดงข้อมูล) แต่ไม่มีขั้นตอน "Control" ที่ระบบชัดเจน [...] เพิ่ม **Alert Rule Engine** ที่ผูก CPI/SPI เข้ากับ Notification — เมื่อค่าตกต่ำกว่า threshold ให้สร้าง Issue อัตโนมัติในโมดูล Issues ที่มีอยู่แล้ว (ปิด Loop จาก Monitor กลับไปสู่ Control)

**ปัญหาที่แท้จริง:** [[20260815-001-earned-value-monitoring|SPEC-001]] ทำให้ระบบ *วัด* ได้ว่าโครงการแพงกว่าแผนหรือช้ากว่าแผน แต่การวัดอย่างเดียวไม่ทำให้อะไรเกิดขึ้น ถ้าไม่มีใครเปิด Dashboard ดู ค่า CPI ที่ตกลงเรื่อย ๆ ก็ไม่ถูกใครรับรู้จนกว่าจะสายเกินแก้ ตำราเน้นว่า Planning-Monitoring-Controlling ต้องเป็น **closed loop** ไม่ใช่แดชบอร์ดให้ดูเฉย ๆ

**ผลที่ต้องการ:** เมื่อตัวเลขบอกว่าโครงการมีปัญหา ระบบต้อง**ผลักงานเข้าหาคน**เอง — สร้าง Issue ที่มีเจ้าของและติดตามได้ พร้อมแจ้งเตือนผู้เกี่ยวข้อง โดยไม่ต้องรอให้ใครเปิดดู

## 2. ขอบเขต

### อยู่ในขอบเขต

- กฎเตือนบนค่า CPI และ SPI ตามเกณฑ์คงที่ที่ SPEC-001 กำหนดไว้แล้ว
- การประเมินกฎอัตโนมัติหลังบันทึก snapshot รายสัปดาห์
- การสร้าง Issue อัตโนมัติในโมดูล Issues ที่มีอยู่แล้ว
- **การสร้างกลไกการแจ้งเตือนภายในระบบ (in-app notification) ขึ้นใหม่** — ระบบเดิมยังไม่มี ขอบเขตจำกัดเท่าที่ FR-002-13 ถึง FR-002-15 ต้องใช้ คือ สร้างการแจ้งเตือน ส่งถึงผู้รับตามบทบาท ลิงก์ไปยังปลายทาง และหน้ารายการย้อนหลัง
- กลไกกันการแจ้งซ้ำเมื่อเงื่อนไขค้างอยู่หลายงวด

### ไม่อยู่ในขอบเขต

- **กฎที่ผู้ใช้ตั้งเองได้** — รอบนี้ใช้เกณฑ์ตายตัว ไม่มีหน้าจอจัดการกฎ การเปลี่ยนเกณฑ์ต้องแก้โค้ด
- **กฎบนตัวชี้วัดอื่น** — SV, CV, จำนวน Issue ค้าง, งานล่าช้า, วัสดุขาด และอื่น ๆ ทั้งหมด
- **ช่องทางแจ้งเตือนภายนอกระบบ** — อีเมล, LINE, SMS, push notification
- **ความสามารถของกลไกแจ้งเตือนที่เกินกว่า FR-002-13 ถึง FR-002-15** — สถานะอ่าน/ยังไม่อ่าน ตัวนับบนไอคอน กดอ่านทั้งหมด และการตั้งค่าการรับรายผู้ใช้
- **การเชื่อมกับ Crash Analysis** เมื่อ SPI ต่ำกว่าเกณฑ์ — ยังไม่มีโมดูล Crash Analysis ในระบบ รอ spec แยก
- **การเตือนบนมิติ Quality/Specifications** — ยังไม่มีข้อมูลคุณภาพในระบบ

## 4. ผู้เกี่ยวข้อง (Actors)

## 8. User Stories

- ในฐานะ**ผู้บริหาร** ฉันต้องการให้ระบบแจ้งฉันเองเมื่อโครงการมีปัญหา เพื่อไม่ต้องคอยเปิด Dashboard ดูทุกวันว่ามีอะไรผิดปกติหรือไม่
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการให้ปัญหาที่ระบบตรวจพบกลายเป็น Issue ที่มีเจ้าของและติดตามได้ ไม่ใช่แค่ตัวเลขสีแดงบนหน้าจอที่ไม่มีใครรับผิดชอบ
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการให้ระบบเพิ่ม comment ในใบเดิมแทนการสร้างใบใหม่ทุกสัปดาห์ เพื่อไม่ให้รายการ Issue ท่วมจนหาของจริงไม่เจอ
- ในฐานะ**ผู้บริหาร** ฉันต้องการให้ Issue ยังค้างอยู่แม้ตัวเลขจะกลับมาดีแล้ว เพื่อให้มีการทบทวนว่าเกิดอะไรขึ้นและแก้ด้วยอะไร ไม่ใช่หายไปเงียบ ๆ

## 9. เกณฑ์การยอมรับ (Acceptance Criteria)

1. เมื่อ snapshot ของงวดหนึ่งบันทึกค่า CPI = 0.85 ระบบต้องสร้าง Issue 1 ใบ มอบหมายให้ผู้จัดการโครงการ และส่งการแจ้งเตือนถึงผู้จัดการโครงการกับผู้บริหาร
2. เมื่องวดถัดไป CPI = 0.83 และ Issue ใบเดิมยังไม่ปิด ระบบต้องไม่สร้างใบใหม่ แต่ต้องเพิ่ม comment ที่ระบุค่าและงวดใหม่ลงในใบเดิม
3. เมื่องวดถัดมา CPI = 1.05 ระบบต้องเพิ่ม comment ว่าค่ากลับเข้าเกณฑ์แล้ว และ Issue ต้องยังอยู่ในสถานะเปิด
4. เมื่อผู้จัดการโครงการปิด Issue แล้ว และอีก 3 งวดถัดมา CPI ตกลงมาที่ 0.88 อีกครั้ง ระบบต้องสร้าง Issue ใบใหม่ที่อ้างอิงถึงใบที่ปิดไปแล้ว
5. เมื่อ SPI = 0.95 ระบบต้องส่งการแจ้งเตือนแต่ต้องไม่สร้าง Issue
6. เมื่อโครงการยังไม่ได้ตั้ง baseline จน SPI คำนวณไม่ได้ ระบบต้องไม่สร้าง Issue ของกฎ SPI และต้องบันทึกว่าข้ามการประเมินเพราะไม่มี baseline
7. เมื่อประมวลผล snapshot ของงวดเดิมซ้ำเป็นครั้งที่สอง ต้องไม่มี Issue หรือการแจ้งเตือนเพิ่มขึ้นเลย
8. เมื่อการสร้าง Issue ล้มเหลว snapshot ของงวดนั้นต้องยังถูกบันทึกครบถ้วน และความล้มเหลวต้องปรากฏในบันทึกผลการประเมิน
9. เมื่องวดหนึ่งมี CPI = 0.85 และ SPI = 0.88 พร้อมกัน ระบบต้องสร้าง Issue 2 ใบแยกกัน ใบหนึ่งของกฎ CPI และอีกใบของกฎ SPI
10. เมื่อระบบมีผู้ใช้สิทธิ์ระดับผู้บริหาร 3 คน การเข้าเงื่อนไขหนึ่งครั้งต้องส่งการแจ้งเตือนถึงทั้ง 3 คน พร้อมผู้จัดการของโครงการนั้น
11. เมื่อโครงการถูกเปลี่ยนเป็นสถานะพักงาน งวดถัดไปต้องไม่มีการประเมินกฎ ไม่มี Issue ใหม่ และไม่มีการแจ้งเตือน แต่ Issue ที่เปิดค้างอยู่ก่อนหน้าต้องยังคงเปิดอยู่
12. เมื่อโครงการกลับสู่สถานะดำเนินงานและงวดถัดไปยังเข้าเงื่อนไขเดิม ระบบต้องเพิ่ม comment ในใบเดิมที่ค้างอยู่ ไม่สร้างใบใหม่

## 10. ข้อสมมติและคำถามที่ยังค้าง

### ข้อสมมติ

| # | ข้อสมมติ | ที่มา |
| --- | --- | --- |
| A1 | โมดูล Issues ที่มีอยู่แล้วรองรับการสร้าง Issue จากระบบ การกำหนดผู้รับผิดชอบ และการเพิ่ม comment ได้ | เอกสารต้นทางระบุว่าโมดูล Issues มีอยู่แล้ว |
| A2 | **ระบบยังไม่มีกลไกการแจ้งเตือนภายในระบบ ต้องสร้างขึ้นใหม่ในขอบเขตนี้** ตาม FR-002-18 | ยืนยันโดยผู้ใช้ 2026-08-15 |
| A3 | แต่ละโครงการระบุได้ว่าใครเป็นผู้จัดการโครงการ และระบบแยกแยะผู้ใช้ที่มีสิทธิ์ระดับผู้บริหารได้ | จำเป็นต่อ FR-002-07 และ FR-002-13 |
| A4 | โครงการมีสถานะที่แยก "ดำเนินงาน" ออกจาก "ปิด" และ "พักงาน" ได้อยู่แล้ว | จำเป็นต่อ FR-002-17 |

### การตัดสินใจที่ผู้ใช้ยืนยันแล้ว (2026-08-15)

รายการต่อไปนี้ตามมาจากคำตอบที่ได้รับโดยตรง ผู้เขียนตัดสินใจแทนในตอนแรกและผู้ใช้ยืนยันทั้งชุดแล้ว:

- **ประเมินกฎเฉพาะหลัง snapshot รายสัปดาห์** ไม่ประเมินตอนเปิด Dashboard (BR-002-02) เพราะ SPEC-001 ให้คำนวณสดทุกครั้งที่เปิดหน้า ถ้าประเมินกฎด้วยจะยิงแจ้งเตือนทุกครั้งที่มีคนเปิดดู
- **ระดับเหลืองแจ้งเตือนอย่างเดียว ไม่สร้าง Issue** (BR-002-06) เพราะระดับเฝ้าระวังยังไม่ใช่ปัญหาที่ต้องมีคนรับผิดชอบ ถ้าสร้าง Issue ทุกครั้งที่เหลือง รายการจะเต็มไปด้วยเรื่องที่ยังไม่ต้องทำอะไร
- **ไม่ปิด Issue อัตโนมัติเมื่อค่ากลับมาดี** (BR-002-04) เพราะการที่ตัวเลขกลับมาดีไม่ได้แปลว่ามีใครแก้อะไร อาจเป็นแค่ความผันผวนของงวด การปิดอัตโนมัติจะลบหลักฐานว่าเคยมีปัญหา
- **ข้อความต้องอ่านรู้เรื่องโดยไม่ต้องรู้ศัพท์ EVM** เพราะผู้รับการแจ้งเตือนคือผู้บริหาร ไม่ใช่คนที่คุ้นกับ CPI/SPI

### ข้อจำกัดที่รู้ตัว

**ผู้บริหารทุกคนได้รับการแจ้งเตือนของทุกโครงการ** (BR-002-08) ทางเลือกนี้เรียบง่ายและไม่ต้องมีข้อมูลจับคู่ผู้บริหารกับโครงการ แต่เมื่อระบบมีโครงการพร้อมกันหลายโครงการ ผู้บริหารจะได้รับการแจ้งเตือนที่ไม่เกี่ยวกับตนจำนวนมาก ซึ่งเป็นต้นทางของ alert fatigue — สุดท้ายไม่มีใครอ่าน และกลไกทั้งหมดก็ไร้ผล

เมื่อจำนวนโครงการที่ดำเนินงานพร้อมกันเริ่มมาก ควรออก spec ใหม่เพื่อจับคู่ผู้บริหารกับโครงการ หรือเพิ่มการตั้งค่าให้ผู้ใช้เลือกรับเฉพาะโครงการที่สนใจ กฎอื่นใน SPEC-002 ใช้ต่อได้โดยไม่ต้องแก้

### คำถามที่ยังค้าง

ไม่มีคำถามค้าง — คำถามทั้ง 3 ข้อได้รับคำตอบเมื่อ 2026-08-15 และถูกแปลงเป็น BR-002-03 (Issue แยกใบตามกฎ), BR-002-08 (ผู้รับการแจ้งเตือน) และ FR-002-17 กับ BR-002-07 (หยุดประเมินเมื่อโครงการปิดหรือพักงาน) เรียบร้อยแล้ว

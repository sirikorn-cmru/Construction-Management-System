# SPEC-001 — การติดตามโครงการด้วย Earned Value (EVM)

## 1. ที่มาและวัตถุประสงค์

ที่มาจากเอกสารเทียบเนื้อหา Chapter 10 (Monitoring and Information Systems) กับระบบ BuildTrack ซึ่งสรุปข้อสังเกตหลักไว้ว่า:

> Dashboard ปัจจุบันแสดง **% ความคืบหน้า (68%)** และ **% งบใช้ไป (42%)** เป็น **2 ตัวเลขแยกกันโดยสิ้นเชิง** — นี่คือจุดอ่อนใหญ่ที่สุดของระบบตามหลัก Chapter 10 เพราะตัวเลข 2 ตัวนี้แยกกันไม่บอกอะไรเลยว่าโครงการ "คุ้มค่าเงิน" หรือไม่

**ปัญหาที่แท้จริง:** ตัวเลข 2 ตัวบน Dashboard ตอบคำถามว่า "โครงการนี้ดีหรือไม่ดี" ไม่ได้ เพราะไม่มีค่าอ้างอิงว่า ณ จุดเวลานี้ **ควรจะ** คืบหน้าและใช้งบไปเท่าไร (BCWS) การเทียบต้นทุนจริงกับงบรวมทั้งโครงการทำให้ดูเหมือน "งบเหลือเยอะ" ทั้งที่โครงการอาจล่าช้ากว่าแผนมาก

**ผลที่ต้องการ:** ผู้บริหารเปิด Dashboard แล้วรู้ทันทีว่าโครงการ **แพงกว่าแผนหรือช้ากว่าแผน** เป็นตัวเลขเชิงปริมาณ (CPI/SPI/SV/CV) ไม่ใช่ label "ล่าช้า/ไม่ล่าช้า" อย่างที่เป็นอยู่

## 2. ขอบเขต

### อยู่ในขอบเขต

- **Baseline ของ BCWS** — ตั้งค่าของทุกงวดตอนวางแผน แล้วล็อกไม่ให้แก้ย้อนหลัง
- การเก็บและคำนวณค่าหลัก 3 ค่า — BCWS, BCWP, ACWP
- ค่าที่ได้จากการคำนวณ — SV, CV, CPI, SPI
- การ์ด Earned Value บน Dashboard แทนการ์ด % แยก 2 ใบ
- Earned Value Chart แบบเส้นเทียบ BCWS / ACWP / BCWP
- เกณฑ์สีเตือนตามค่า CPI/SPI
- Snapshot รายสัปดาห์เพื่อเก็บประวัติสำหรับวาดกราฟย้อนหลัง

### ไม่อยู่ในขอบเขต

รายการต่อไปนี้อยู่ในเอกสารต้นทางแต่แยกไปเป็น spec ฉบับอื่น เพื่อให้ SPEC-001 จบและใช้งานได้เร็ว:

- **Alert Rule Engine** — การผูก CPI/SPI เข้ากับ Notification และการสร้าง Issue อัตโนมัติเมื่อค่าตกต่ำกว่าเกณฑ์ (ขั้น "Control" ของ closed loop)
- **มิติ Quality/Specifications** — subjective rating A–E และการตรวจคุณภาพงาน
- **รูปแบบการเก็บข้อมูลอื่น** — frequency counts, raw numbers, trend ของ Issue
- **การเชื่อมกับ Crash Analysis** เมื่อ SPI ต่ำกว่าเกณฑ์
- **การคำนวณ BCWS อัตโนมัติจากงบประมาณต่องานใน WBS** — รอบนี้ผู้วางแผนกรอกค่า baseline ของแต่ละงวดเอง ดู [ข้อ 9](#9-ข้อสมมติและคำถามที่ยังค้าง)

## 3. ผู้เกี่ยวข้อง (Actors)

| Actor | บทบาทในขอบเขตนี้ |
| --- | --- |
| ผู้จัดการโครงการ (PM) | ตั้ง baseline BCWS ของทุกงวดตอนวางแผน และขออนุมัติ re-baseline เมื่อขอบเขตงานเปลี่ยน |
| ผู้บริหาร | ดูการ์ด EV และกราฟบน Dashboard เพื่อประเมินสถานะโครงการ และเป็นผู้อนุมัติ re-baseline |
| ระบบ (อัตโนมัติ) | คำนวณ BCWP/ACWP/ดัชนี บันทึก snapshot รายสัปดาห์ และบังคับกฎการล็อก baseline |

## 4. ความต้องการเชิงหน้าที่ (Functional Requirements)

| --- | --- | --- |

| FR-001-04 | ระบบแสดงว่าดัชนีที่เห็นอยู่คำนวณจาก baseline เวอร์ชันใด และเปิดดูรายการ baseline ทุกเวอร์ชันพร้อมเหตุผลของการเปลี่ยนได้ | Must |

| FR-001-16 | เมื่อโครงการเคย re-baseline กราฟแสดงเส้น BCWS ของเวอร์ชันเก่าเป็น**เส้นจาง** ควบคู่กับเวอร์ชันปัจจุบันที่เป็น**เส้นทึบ** เพื่อให้เห็นว่าแผนถูกเลื่อนไปเท่าไร | Must |

## 6. กฎทางธุรกิจ (Business Rules)

| ID | กฎ |
| --- | --- |
| BR-001-01 | **BCWS เป็น baseline ที่ล็อกแล้ว** เมื่อยืนยันครั้งแรก ห้ามแก้ไขหรือลบไม่ว่ากรณีใด การเปลี่ยนแปลงทำได้ทางเดียวคือสร้าง baseline เวอร์ชันใหม่ |
| BR-001-02 | Baseline เวอร์ชันใหม่ต้องมีเหตุผล ผู้อนุมัติ วันที่มีผล และ**งบประมาณรวมโครงการ (BAC)** ครบทั้ง 4 อย่าง จึงจะบันทึกได้ — คำขอที่ไม่ได้เปลี่ยนงบก็ต้องระบุค่าเดิมซ้ำ เพื่อให้ทุกเวอร์ชันมี BAC ครบโดยไม่ต้องมีตรรกะสืบทอด |
| BR-001-03 | ดัชนีของงวดใด ๆ คำนวณจาก baseline เวอร์ชันที่มีผลอยู่ ณ งวดนั้น — การ re-baseline ไม่เปลี่ยนตัวเลขของงวดที่ผ่านมาแล้ว |
| BR-001-04 | BCWP = (% ความคืบหน้ารวมของโครงการ) × **BAC** โดย BAC มีที่มาและกฎ fallback ตาม BR-001-11 — ไม่ใช่ค่าจากแหล่งอื่น |
| BR-001-05 | เกณฑ์สี: CPI/SPI ≥ 1.0 = เขียว, 0.9 ≤ ค่า < 1.0 = เหลือง (เฝ้าระวัง), ค่า < 0.9 = แดง (ต้องแก้ไขด่วน) |
| BR-001-06 | เมื่อ ACWP = 0 หรือ BCWS = 0 ระบบต้องแสดง "—" แทนค่าดัชนี ห้ามแสดง 0 หรือค่าอนันต์ |
| BR-001-07 | Snapshot เป็นแบบ append-only ห้ามลบและห้ามแก้ หนึ่งงวดมีได้หนึ่ง snapshot |
| BR-001-08 | งวดเริ่มวันจันทร์และสิ้นสุดวันอาทิตย์ งวดแรกนับจากวันเริ่มโครงการถึงวันอาทิตย์ถัดไป และงวดสุดท้ายสิ้นสุดที่วันสิ้นสุดโครงการ ทั้งสองงวดจึงอาจสั้นกว่า 7 วัน แต่ยังถือเป็นหนึ่งงวดเต็มในการคำนวณ |
| BR-001-09 | ผู้บริหารเป็นผู้อนุมัติคำขอ re-baseline และ**ผู้ยื่นคำขอจะอนุมัติคำขอของตนเองไม่ได้** แม้จะมีสิทธิ์ระดับผู้บริหารก็ตาม |
| BR-001-10 | Earned Value Chart แสดงเส้น BCWS ของ baseline เวอร์ชันเก่าได้สูงสุด 2 เวอร์ชันล่าสุด เวอร์ชันที่เก่ากว่านั้นดูได้ในหน้าประวัติ baseline เพื่อไม่ให้กราฟอ่านไม่ออก |
| BR-001-11 | **EAC = BAC / CPI** โดย **BAC คือช่องงบประมาณรวมโครงการของ `Schedule_Baseline` เวอร์ชันที่มีผล ณ งวดนั้น** ตาม BR-001-03 — เมื่องวดใดยังไม่มี baseline ที่มีผล ระบบใช้**มูลค่าสัญญาจาก `Contract` เป็น BAC แทน (fallback)** เพื่อให้ BCWP, CPI, CV และ EAC คำนวณได้ตาม FR-001-13 สูตรนี้สมมติว่าประสิทธิภาพต้นทุนที่ผ่านมาจะดำเนินต่อไป และให้ค่าเดียวต่อโครงการเสมอจึงเทียบข้ามโครงการได้ |
| BR-001-12 | เมื่อ CPI คำนวณไม่ได้ (ACWP = 0) ระบบต้องแสดง EAC, ETC และ VAC เป็น "—" ตามหลักเดียวกับ BR-001-06 ห้ามแสดงค่าอนันต์ |
| BR-001-13 | **การ fallback มีผลเฉพาะงวดที่ยังไม่มี baseline** — เมื่อตั้ง baseline ที่มีผลตั้งแต่งวดหนึ่ง งวดก่อนหน้ายังใช้มูลค่าสัญญาต่อไปและไม่ถูกคำนวณย้อนหลัง ตาม BR-001-07 ที่ห้ามแก้ snapshot |
| BR-001-14 | เมื่อโครงการไม่มีทั้ง baseline ที่มีผลและมูลค่าสัญญาใน `Contract` ระบบต้องแสดง BCWP, CPI, CV, EAC, ETC และ VAC เป็น "—" พร้อมข้อความ "ยังไม่มีงบประมาณรวมโครงการ" ตามหลักเดียวกับ BR-001-06 — ห้ามใช้ 0 เป็นค่าตั้งต้นของ BAC |

## 7. User Stories

- ในฐานะ**ผู้บริหาร** ฉันต้องการเห็นค่า CPI และ SPI พร้อมสีเตือนบน Dashboard เพื่อรู้ได้ในไม่กี่วินาทีว่าโครงการแพงกว่าแผนหรือช้ากว่าแผน
- ในฐานะ**ผู้บริหาร** ฉันต้องการมั่นใจว่า BCWS ที่ใช้เทียบไม่ถูกแก้ย้อนหลัง เพื่อให้ตัวเลข SV และ SPI ที่เห็นเชื่อถือได้จริง
- ในฐานะ**ผู้บริหาร** ฉันต้องการเห็นกราฟเทียบ BCWS/ACWP/BCWP ในภาพเดียว เพื่อดูแนวโน้มว่าปัญหากำลังแย่ลงหรือดีขึ้น ไม่ใช่เห็นแค่ค่า ณ วันนี้
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการตั้ง baseline BCWS ของทุกงวดตอนวางแผนครั้งเดียว เพื่อไม่ต้องมากรอกซ้ำทุกสัปดาห์ระหว่างดำเนินงาน
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการขอ re-baseline เมื่อขอบเขตงานเปลี่ยนจริง เพื่อให้ดัชนีสะท้อนแผนที่ใช้อยู่ โดยที่ประวัติของแผนเดิมยังตรวจสอบได้

## 8. เกณฑ์การยอมรับ (Acceptance Criteria)

1. เมื่อโครงการมี % ความคืบหน้า 68%, งบรวม 50M, ยอดเบิกจ่ายจริง 21M และ baseline กำหนด BCWS ของงวดนี้ไว้ 30M ระบบต้องแสดง BCWP = 34M, SV = +4M, CV = +13M, CPI = 1.62, SPI = 1.13
2. เมื่อ CPI = 1.62 การ์ดต้องแสดงเป็นสีเขียว และเมื่อ CPI = 0.85 ต้องแสดงเป็นสีแดง
3. เมื่อพยายามแก้ค่า BCWS ของงวดใดก็ตามหลังยืนยัน baseline แล้ว ระบบต้องปฏิเสธ ทั้งผ่านหน้าจอและผ่านการเรียก API ตรง
4. เมื่อสร้าง baseline เวอร์ชัน 2 มีผลตั้งแต่งวดที่ 10 ค่าดัชนีของงวดที่ 1–9 ต้องไม่เปลี่ยนจากเดิม และงวดที่ 10 เป็นต้นไปต้องใช้ค่าจากเวอร์ชัน 2
5. เมื่อโครงการยังไม่ได้ตั้ง baseline การ์ดต้องแสดง "ยังไม่ได้ตั้ง baseline" และซ่อนค่า SPI กับ SV โดยยังแสดง CV และ CPI ได้ตามปกติ
6. เมื่อผ่านไป 4 สัปดาห์ Earned Value Chart ต้องมีจุดข้อมูลของทั้ง 3 เส้นครบ 4 จุด โดยไม่ต้องให้ผู้ใช้กดสร้างเอง
7. เมื่อโครงการเริ่มวันพุธ งวดที่ 1 ต้องสิ้นสุดวันอาทิตย์ถัดไป (ยาว 5 วัน) และงวดที่ 2 ต้องเริ่มวันจันทร์ถัดมา
8. เมื่อผู้บริหารเป็นผู้ยื่นคำขอ re-baseline เอง ระบบต้องไม่ยอมให้กดอนุมัติคำขอนั้น และต้องรอผู้บริหารคนอื่นอนุมัติ
9. เมื่อโครงการมี baseline 3 เวอร์ชัน กราฟต้องแสดงเส้นจางของเวอร์ชัน 1 และ 2 พร้อมเส้นทึบของเวอร์ชัน 3 และเมื่อมี 4 เวอร์ชัน ต้องแสดงเส้นจางเฉพาะเวอร์ชัน 2 กับ 3
10. เมื่องบรวมโครงการ 50M และ CPI = 0.80 ระบบต้องแสดง EAC = 62.5M และ VAC = −12.5M
11. เมื่อ ACWP = 0 จน CPI คำนวณไม่ได้ ระบบต้องแสดง EAC, ETC และ VAC เป็น "—" ไม่ใช่ค่าอนันต์
12. เมื่อโครงการ re-baseline แล้วงบรวมเปลี่ยน ค่า EAC ของงวดก่อนวันที่มีผลของ baseline ใหม่ต้องไม่เปลี่ยน
13. เมื่อโครงการยังไม่มี baseline โดยมีมูลค่าสัญญา 50M, % ความคืบหน้า 68% และ ACWP 21M ระบบต้องแสดง BCWP = 34M, CV = +13M, CPI = 1.62 พร้อม EAC/ETC/VAC ที่คำนวณจาก BAC = 50M โดยยังซ่อน SPI และ SV
14. เมื่อตั้ง baseline ครั้งแรกด้วยงบรวม 55M ให้มีผลตั้งแต่งวดที่ 5 ค่าของงวดที่ 1–4 ต้องยังใช้ BAC 50M จาก `Contract` และไม่ถูกคำนวณย้อนหลัง
15. เมื่อคำขอ re-baseline ระบุงบรวมใหม่ 60M และได้รับอนุมัติให้มีผลตั้งแต่งวดที่ 10 EAC ของงวดที่ 10 เป็นต้นไปต้องคำนวณจาก 60M ส่วนงวดที่ 1–9 ต้องไม่เปลี่ยน
16. เมื่อโครงการไม่มีทั้ง baseline และมูลค่าสัญญา ระบบต้องแสดง BCWP, CPI, CV, EAC, ETC และ VAC เป็น "—" พร้อมข้อความ "ยังไม่มีงบประมาณรวมโครงการ"
17. เมื่อ CPI คำนวณได้ปกติ การ์ด Earned Value ต้องแสดงครบทั้ง EAC, ETC และ VAC พร้อมข้อความอธิบายภาษาไทยของแต่ละค่า

### ข้อจำกัดที่รู้ตัว

BCWS ยังต้องกรอกด้วยมือในขั้นวางแผน แม้ `WBS_Task` จะเก็บงบต่องานไว้แล้วตาม FR-003-04 ของ SPEC-003 เพราะ BR-003-09 กำหนดว่ารอบนี้ยังไม่ป้อนงบต่องานเข้า EVM ผลคือความ**แม่นยำ**ของ baseline ขึ้นกับคุณภาพการวางแผนของ PM แต่ความ**น่าเชื่อถือ**ไม่ได้ลดลง เพราะเมื่อยืนยันแล้วค่าถูกล็อกและแก้ย้อนหลังไม่ได้ (BR-001-01)

เมื่อพร้อมเปลี่ยนแกน ควรออก spec ใหม่ให้ระบบคำนวณ BCWS จากงบต่องานใน `WBS_Task` × planned % ให้อัตโนมัติ ซึ่งจะลดภาระการกรอกและตัดความคลาดเคลื่อนจากคนออกไป กฎการล็อกใน SPEC-001 ใช้ต่อได้โดยไม่ต้องแก้

### เกณฑ์ 0.9 กับเป้าหมาย 0.95 ไม่ใช่ตัวเลขชุดเดียวกัน

เอกสาร "ระบบควบคุมงานก่อสร้างเพื่อความสำเร็จของโครงการ" ตั้งเกณฑ์ความสำเร็จไว้ที่ SPI และ CPI เฉลี่ย **ไม่ต่ำกว่า 0.95** ซึ่งดูขัดกับ BR-001-05 ที่ใช้ **0.9** เป็นเส้นแดง — ทั้งสองตัวเลขอยู่ร่วมกันได้เพราะวัดคนละอย่าง:

- **0.9 คือเกณฑ์ปฏิบัติการ** — ใช้กับโครงการหนึ่งในงวดหนึ่ง เพื่อตัดสินสีบนการ์ดและการสร้าง Issue ตาม BR-002-06 ของ SPEC-002
- **0.95 คือเป้าหมายระดับพอร์ตโฟลิโอ** — ค่าเฉลี่ยของทุกโครงการ ใช้ตอบว่าการลงทุนทำระบบนี้ได้ผลหรือไม่ อยู่ใน [[../02-plan/index|02-plan]] ไม่ใช่ในสเปค

การบังคับให้สองตัวเลขนี้ตรงกันเท่ากับเอาตัวชี้วัดผลลัพธ์ไปตั้งเป็น threshold ปฏิบัติการ ซึ่งจะทำให้ Issue ท่วมช่วง 0.9–0.95 โดยไม่ได้ประโยชน์เพิ่ม — ตรงกับเหตุผลที่ BR-002-06 ปฏิเสธการสร้าง Issue ในระดับเหลืองไว้แล้ว

### คำถามที่ยังค้าง

ไม่มีคำถามค้าง — คำถามทั้ง 3 ข้อได้รับคำตอบเมื่อ 2026-08-15 และถูกแปลงเป็นกฎ BR-001-08 (นิยามงวด), BR-001-09 (ผู้อนุมัติ re-baseline) และ BR-001-10 (การแสดงเส้น baseline เก่า) เรียบร้อยแล้ว

### การตัดสินใจที่ผู้ใช้ยืนยันแล้ว (2026-08-15)

รายละเอียดต่อไปนี้ตามมาจากคำตอบข้างต้นโดยตรง ผู้เขียนตัดสินใจแทนในตอนแรกและผู้ใช้ยืนยันทั้งชุดแล้ว:

- **งวดแรกและงวดสุดท้ายที่ไม่ครบ 7 วัน** ยังนับเป็นหนึ่งงวดเต็มในการคำนวณ ไม่ได้เฉลี่ยตามสัดส่วนวัน (BR-001-08)
- **จำกัดเส้น baseline เก่าบนกราฟไว้ที่ 2 เวอร์ชันล่าสุด** เพราะถ้า re-baseline หลายครั้งกราฟจะอ่านไม่ออก ส่วนที่เกินดูได้ในหน้าประวัติ (BR-001-10)
- **ผู้ยื่นคำขอ re-baseline อนุมัติคำขอตนเองไม่ได้** แม้มีสิทธิ์ระดับผู้บริหาร เพราะการอนุมัติคนเดียวจบเท่ากับไม่มีการควบคุมเลย (BR-001-09)

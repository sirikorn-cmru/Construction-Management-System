# SPEC-003 — สถาปัตยกรรมฟังก์ชันของระบบบริหารโครงการก่อสร้าง

เอกสารนี้เป็น **umbrella spec** — กำหนดโครงสร้างส่วนงาน แบบจำลองข้อมูลกลาง และกฎที่ข้ามโมดูล ส่วนรายละเอียดของแต่ละหน้าจอจะถูกแตกเป็น spec ลูกในภายหลัง

## 1. ที่มาและวัตถุประสงค์

> "ออกแบบสถาปัตยกรรมฟังก์ชันการทำงาน (Functional Requirements) ของระบบบริหารโครงการก่อสร้าง แบ่งโครงสร้างการตอบเป็น 3 ส่วน: User Journey สั้นๆ ของลูกค้า / Core Feature List (แบ่งเป็น Customer-facing และ Barista Display System) / Data Entities หลักๆ ที่ต้องใช้ในระบบ"

โจทย์ต้นทางระบุ **"Barista Display System"** ซึ่งเป็นแนวคิดของร้านกาแฟ ไม่มีในระบบก่อสร้าง — ตีความตามเจตนาว่าหมายถึง *หน้าจอของคนที่ลงมือทำงานจริง* จึงแมปเป็น **Site Operations Display** สำหรับโฟร์แมนและผู้ควบคุมงาน และตีความ "ลูกค้า" เป็น **เจ้าของโครงการ (Project Owner)** ผู้ใช้รับทราบและยืนยันการตีความนี้แล้ว

**ปัญหาที่แท้จริง:** [[20260815-001-earned-value-monitoring|SPEC-001]] และ [[20260815-002-alert-rule-engine|SPEC-002]] แก้เรื่องการวัดและการปิด loop ในระดับผู้บริหาร แต่ยังไม่มีเอกสารใดกำหนดว่าระบบทั้งระบบประกอบด้วยกลุ่มผู้ใช้ใด แต่ละกลุ่มเห็นอะไรและทำอะไรได้ และข้อมูลไหลจากหน้างานขึ้นไปเป็นตัวเลข EVM ได้อย่างไร ผลคือฟังก์ชันแกนกลางไม่มีที่อยู่ และไม่มีที่ใดระบุว่าเจ้าของโครงการเห็นอะไรได้บ้าง

**ผลที่ต้องการ:** มีเอกสารเดียวที่ตอบได้ว่าระบบมีกี่ส่วนงาน ข้อมูลอยู่ที่ไหน และกฎที่ทุกโมดูลต้องเคารพคืออะไร เพื่อให้ spec ลูกแต่ละฉบับเขียนได้โดยไม่ขัดกันเอง

## 2. ขอบเขต

### อยู่ในขอบเขต

- นิยามส่วนงาน 3 ส่วนและความรับผิดชอบของแต่ละส่วน
- User Journey ของเจ้าของโครงการ 6 ขั้น
- แบบจำลองข้อมูลหลักและเส้นทางข้อมูลที่ทำให้ EVM ทำงานได้
- กฎการมองเห็นข้อมูลของเจ้าของโครงการ
- กฎการบันทึกความคืบหน้าหน้างาน การประกอบ Daily Report และการทำงานออฟไลน์
- กระบวนการ Change Order และการเชื่อมเข้ากับ re-baseline
- บัญชีฟีเจอร์ที่ spec ลูกต้องครอบคลุม ([ภาคผนวก ก](#ภาคผนวก-ก--บัญชีฟีเจอร์ที่ต้องแตกเป็น-spec-ลูก))

### ไม่อยู่ในขอบเขต

- **การคำนวณและแสดงผล EVM** — อยู่ใน SPEC-001 ไม่เขียนซ้ำ
- **กฎเตือนและการสร้าง Issue อัตโนมัติ** — อยู่ใน SPEC-002 ไม่เขียนซ้ำ
- **การเปลี่ยนแกนคำนวณ BCWP มาเป็นระดับ WBS** — ดู BR-003-09
- **การคำนวณ BCWS อัตโนมัติจากงบต่องานใน `WBS_Task`** — สืบทอดข้อจำกัดจาก SPEC-001 ที่ระบุไว้เองว่าอยู่นอกขอบเขต BCWS ยังมาจากการกรอกด้วยมือ
- **โมดูลประมาณราคาแบบ bottom-up จาก BOQ (REQ-F11 ของเอกสาร Construction Project Control System)** — รับรู้แล้วและถูกเลื่อนไปพร้อมกับการเปลี่ยนแกน BCWS ดู [ข้อ 12](#12-ข้อสมมติและคำถามที่ยังค้าง)
- **รายละเอียดหน้าจอของแต่ละฟีเจอร์** — เป็นหน้าที่ของ spec ลูก
- **การจัดสรรทรัพยากร Crash Analysis การจัดซื้อ และการจัดการผู้รับเหมาช่วง** — อยู่ในกลุ่ม PM & Executive Console แต่ยังไม่มี spec
- **ช่องทางแจ้งเตือนภายนอกระบบ** — สืบทอดข้อจำกัดจาก SPEC-002
- **การเปิดใช้งานสิทธิ์เข้าระบบของผู้รับเหมาช่วง** — โครงสร้างสิทธิ์ที่รองรับอยู่ในขอบเขต (FR-003-19, FR-003-20) แต่การเปิดใช้จริงและสิ่งที่ผู้รับเหมาช่วงเห็นได้ ต้องมี spec แยก

## 3. เอกสารที่เกี่ยวข้อง

| Spec | ความสัมพันธ์ |
| --- | --- |
| [[20260815-001-earned-value-monitoring\|SPEC-001]] | SPEC-003 นิยาม Entity ที่เป็นแหล่งข้อมูลของ BCWS/BCWP/ACWP และเชื่อม Change Order เข้ากับ re-baseline (FR-001-03) การคำนวณยังเป็นของ SPEC-001 ทั้งหมด |
| [[20260815-002-alert-rule-engine\|SPEC-002]] | ใช้ Entity `Issue` และ**ช่องทาง**แจ้งเตือนในระบบร่วมกัน SPEC-003 ไม่เขียนกฎเตือนซ้ำ — **ช่องทางแจ้งเตือนยังไม่มีในระบบ SPEC-002 (FR-002-18) เป็นผู้สร้าง งานฝั่ง Owner Portal ที่พึ่งช่องทางนี้จึงต้องรอ** |

**SPEC-003 นิยามสิทธิ์การเข้าถึงข้อมูลของตัวเอง** (BR-003-12, BR-003-13) ไม่สืบทอดจากกฎผู้รับการแจ้งเตือนของ SPEC-002 — กฎผู้รับการแจ้งเตือนกับกฎการเข้าถึงข้อมูลเป็นคนละเรื่องกัน การอ้างข้ามกันเป็นที่มาของข้อผิดพลาดที่ตรวจพบเมื่อ 2026-08-15

## 4. ส่วนงานและผู้เกี่ยวข้อง

| ส่วนงาน | ผู้ใช้ | ความรับผิดชอบ |
| --- | --- | --- |
| **Owner Portal** | เจ้าของโครงการ | ติดตามความคืบหน้า อนุมัติงวดงาน ยื่น Change Order ตรวจรับและยืนยันการแก้ไข |
| **Site Operations Display** | โฟร์แมน / ผู้ควบคุมงาน | บันทึกความคืบหน้า กำลังคน วัสดุ สภาพอากาศ ปัญหา และผลตรวจคุณภาพที่หน้างาน |
| **PM & Executive Console** | ผู้จัดการโครงการ, ผู้บริหาร | วางแผน WBS ตั้ง baseline ประเมิน Change Order ควบคุมการมองเห็นข้อมูล และดูภาพรวม (Dashboard EVM และ Alert Engine อยู่ใน SPEC-001/002 แล้ว) |

**ผู้รับเหมาช่วง** เป็นบทบาทที่ระบบสิทธิ์ต้องรองรับตั้งแต่ตอนนี้ แต่ยังไม่เปิดใช้ในรอบนี้ — ดู FR-003-19, FR-003-20 และ BR-003-11 การเพิ่มบทบาททีหลังโดยไม่ได้ออกแบบไว้ก่อน แปลว่าต้องรื้อทุกจุดที่ตรวจสิทธิ์ในทุกโมดูล

## 5. User Journey ของเจ้าของโครงการ

| # | ช่วง | เจ้าของโครงการทำอะไร | ระบบให้อะไร |
| --- | --- | --- | --- |
| 1 | ลงนาม–เริ่มงาน | ตรวจขอบเขตงานและแผน | baseline ที่ล็อกแล้ว — งบ เวลา งวดงาน |
| 2 | ติดตามรายสัปดาห์ | ดูว่าช้าหรือเร็วกว่าแผน | ความคืบหน้าเทียบแผน + รูปหน้างานจริง |
| 3 | อนุมัติงวดงาน | ตรวจงานตามงวด อนุมัติหรือตีกลับ | เอกสารงวด รูปประกอบ ประวัติการเบิกจ่าย |
| 4 | ขอเปลี่ยนแปลง | ยื่น Change Order | **ผลกระทบต่อเวลาและงบที่ผูกพัน ก่อนกดยืนยัน** |
| 5 | รับรู้ปัญหา | อ่านเรื่องที่กระทบตน ตัดสินสิ่งที่ต้องตัดสิน | Issue ที่ถูกเปิดเผยต่อลูกค้าเท่านั้น |
| 6 | ตรวจรับ–ส่งมอบ | ตรวจงาน แจ้งจุดแก้ ยืนยันเมื่อแก้เสร็จ | punch list เอกสารส่งมอบ การรับประกัน |

ขั้นที่ 4 คือจุดชี้ขาด — ระบบส่วนใหญ่ให้ลูกค้าขอเปลี่ยนแปลงได้โดยไม่เห็นราคาของการเปลี่ยน ผลคือข้อพิพาทตอนวางบิล

### เส้นทางข้อมูลของ EVM

```
ค่าที่ผู้วางแผนกรอก ──► Schedule_Baseline (ล็อก) ──► BCWS
                                    └──────────────► BAC ──► BCWP, EAC
Contract (มูลค่าสัญญา) ──► BAC เมื่องวดนั้นยังไม่มี baseline (fallback)
Progress_Update ─────────────────────────────────► BCWP
Payment ─────────────────────────────────────────► ACWP
                                                    └──► EV_Snapshot ──► Alert_Event ──► Issue

WBS_Task (งบต่องาน) ──► เก็บไว้เพื่ออนาคต ยังไม่ป้อนเข้า EVM ในรอบนี้
```

> `EV_Snapshot` อ้าง `Schedule_Baseline` แบบ **0–1** ไม่ใช่ 1–1 เพราะงวดที่ยังไม่มี baseline ที่มีผลก็ต้องมี snapshot ได้ โดยใช้มูลค่าสัญญาเป็น BAC ตาม BR-001-11 — รายละเอียดของสิ่งที่ snapshot ต้องบันทึกอยู่ใน **BR-001-15 ของ SPEC-001** ซึ่งเป็นเจ้าของกฎการคำนวณ ส่วนสเปคนี้เป็นเจ้าของแบบจำลองข้อมูลเท่านั้น

**ข้อควรรู้:** แผนภาพนี้แสดงว่าข้อมูลมาจากไหน ไม่ใช่สูตรคำนวณ **BCWS มาจากค่าที่ผู้วางแผนกรอกและล็อกไว้** ตาม FR-001-01 และข้อสมมติ A5 ของ SPEC-001 ไม่ได้ derive จากงบต่องานใน `WBS_Task` ส่วน **BCWP** คำนวณจาก % รวมทั้งโครงการ × งบรวม ตาม BR-001-04 งบต่องานใน `WBS_Task` เก็บไว้เพื่อให้เปลี่ยนแกนได้ในอนาคตเท่านั้น — ดู BR-003-09

## 10. User Stories

- ในฐานะ**เจ้าของโครงการ** ฉันต้องการเห็นผลกระทบต่อเวลาและงบที่ผูกพันก่อนกดยืนยัน Change Order เพื่อไม่ต้องมาเถียงเรื่องราคาตอนวางบิล
- ในฐานะ**เจ้าของโครงการ** ฉันต้องการมั่นใจว่าข้อมูลภายในของผู้รับเหมาไม่หลุดมาถึงฉันโดยบังเอิญ เพราะนั่นทำให้ความสัมพันธ์ในสัญญาเสียหาย
- ในฐานะ**โฟร์แมน** ฉันต้องการกดบันทึกความคืบหน้าไม่กี่ครั้งด้วยมือที่สวมถุงมือ เพื่อไม่ต้องเลี่ยงไปจดใส่กระดาษแล้วมากรอกตอนเย็น
- ในฐานะ**โฟร์แมน** ฉันต้องการให้ Daily Report ประกอบขึ้นเองจากสิ่งที่ฉันบันทึกไประหว่างวัน เพื่อไม่ต้องกรอกเรื่องเดิมซ้ำสองรอบ
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการให้ระบบบังคับว่าหน้างานเห็นเฉพาะแบบฉบับล่าสุด เพราะการใช้แบบเก่าคือสาเหตุของงานรื้อทำใหม่
- ในฐานะ**ผู้จัดการโครงการ** ฉันต้องการให้ข้อมูลที่ชนกันตอน sync มาให้ฉันตัดสิน เพื่อไม่ให้ความคืบหน้าที่ทีมบันทึกไว้หายไปเงียบ ๆ

## 11. เกณฑ์การยอมรับ (Acceptance Criteria)

1. เมื่อผู้ใช้บทบาทเจ้าของโครงการเรียก API ที่คืนต้นทุนภายในโดยตรง ระบบต้องปฏิเสธ ไม่ใช่แค่ซ่อนบนหน้าจอ
2. เมื่อสร้าง `Issue` ใหม่ ไม่ว่าคนสร้างหรือ SPEC-002 สร้าง ธง "เปิดเผยต่อลูกค้า" ต้องเป็นปิด และ Issue นั้นต้องไม่ปรากฏในพอร์ทัลจนกว่าจะมีผู้กดเปิด
3. เมื่อโฟร์แมนบันทึกความคืบหน้า ระบบต้องรับได้เฉพาะค่า 0 / 50 / 100 และปฏิเสธค่าอื่นทั้งจากหน้าจอและจาก API
4. เมื่อสิ้นวัน Daily Report ต้องมีข้อมูลกำลังคน วัสดุ สภาพอากาศ และความคืบหน้าครบตามที่บันทึกไว้ระหว่างวัน โดยไม่มีช่องให้กรอกเนื้อหาเหล่านั้นซ้ำ
5. เมื่ออุปกรณ์ออฟไลน์ทั้งวันแล้วกลับมามีสัญญาณ ข้อมูลที่บันทึกไว้ทั้งหมดต้องขึ้นระบบครบตามลำดับเวลาที่บันทึก
6. เมื่อโฟร์แมนสองคนบันทึกความคืบหน้าของงานเดียวกันขณะออฟไลน์ ระบบต้องแสดงทั้งสองค่าให้คนตัดสิน และต้องไม่ทับค่าใดค่าหนึ่งเอง
7. เมื่ออุปกรณ์อยู่ในโหมดออฟไลน์และเปิดแบบก่อสร้างที่ cache ไว้ ระบบต้องแสดงคำเตือนพร้อมเวลาที่ sync ครั้งสุดท้าย
8. เมื่อเจ้าของโครงการยื่น Change Order ระบบต้องไม่แสดงตัวเลขผลกระทบใด ๆ จนกว่าผู้จัดการโครงการจะประเมินและตอบกลับ
9. เมื่อเจ้าของโครงการยืนยัน Change Order ระบบต้องสร้างคำขอ re-baseline ที่รออนุมัติ และต้องไม่เปลี่ยน `Schedule_Baseline` ที่มีผลอยู่
10. เมื่อผู้ใช้ที่ไม่ได้เป็นสมาชิกของโครงการเรียกดูข้อมูลของโครงการนั้น ระบบต้องปฏิเสธ — **ยกเว้นผู้ใช้สิทธิ์ระดับผู้บริหาร ซึ่งเห็นชนิดข้อมูลในรายการปิดตาม BR-003-12 และเปิด Issue ที่ระบบสร้างจากกฎ EVM ได้ตาม BR-003-13 รายละเอียดของข้อยกเว้นอยู่ในเกณฑ์ข้อ 11 และ 12**
11. เมื่อผู้ใช้สิทธิ์ระดับผู้บริหารที่ไม่ได้เป็นสมาชิกเรียกดัชนี EVM ค่าพยากรณ์ EAC/ETC/VAC และ milestone ของโครงการหนึ่ง ระบบต้องคืนค่าให้ แต่เมื่อเรียกสัญญา ต้นทุนภายใน หรือข้อพิพาทของโครงการเดียวกัน ต้องปฏิเสธ — และเมื่อเจ้าของโครงการเรียก EAC/ETC/VAC ต้องถูกปฏิเสธเช่นกัน
12. เมื่อผู้บริหารที่ไม่ได้เป็นสมาชิกกดลิงก์จากการแจ้งเตือนไปยัง Issue ที่ระบบสร้างจากกฎ EVM ต้องเปิดได้ แต่เมื่อเปิด Issue ที่คนสร้างในโครงการเดียวกัน ต้องถูกปฏิเสธ
13. เมื่อ Change Order ถูกยืนยันแล้ว ระบบต้องสร้างคำขอ re-baseline ที่มีผู้จัดการโครงการเป็นผู้ยื่น มีวันที่มีผลตรงกับช่องวันที่มีผลของ Change Order และมีเหตุผลอ้างเลขที่ Change Order นั้น
14. เมื่อผู้จัดการโครงการที่มีสิทธิ์ระดับผู้บริหารพยายามอนุมัติคำขอ re-baseline ที่ตนเป็นผู้ยื่น ระบบต้องปฏิเสธตาม BR-001-09
15. เมื่อคำขอ re-baseline ที่มาจาก Change Order ถูกปฏิเสธ ตัวเลขผลกระทบที่ลูกค้ายืนยันไว้ต้องยังคงอยู่ `Schedule_Baseline` ต้องไม่เปลี่ยน และระบบต้องเปิด Issue ให้ผู้จัดการโครงการ
16. เมื่อเพิ่มบทบาทใหม่เข้าระบบและกำหนดกฎการมองเห็นของบทบาทนั้น กฎต้องมีผลทันทีในทุกโมดูล โดยไม่ต้องแก้โค้ดตรวจสิทธิ์ที่ใดเลย
17. เมื่อเพิ่มชุดผู้รับการแจ้งเตือนใหม่สำหรับชนิดเหตุการณ์หนึ่ง กลไกแจ้งเตือนเดิมต้องไม่ต้องถูกแก้
18. เมื่อเจ้าของโครงการเรียก API ที่คืน EAC, ETC หรือ VAC ของโครงการที่ตนเป็นเจ้าของ ระบบต้องปฏิเสธที่ชั้นข้อมูล ไม่ใช่แค่ซ่อนบนหน้าจอ
19. เมื่อ Owner Portal เรียกชนิดข้อมูลที่ไม่ปรากฏในรายการอนุญาต ระบบต้องปฏิเสธโดยไม่ต้องมีใครเพิ่มชนิดนั้นเข้า deny-list ก่อน
20. เมื่อ BAC ที่มีผลคือ 50M และมี Change Order ที่ยืนยันแล้วยังไม่เข้า baseline สองใบ มูลค่า +3M และ +2M งบรวมใหม่ในคำขอ re-baseline ต้องเป็น 55M ไม่ใช่ 52M หรือ 53M
21. เมื่อโครงการไม่มีทั้ง baseline และมูลค่าสัญญา แล้วลูกค้ายืนยัน Change Order ระบบต้องไม่เติมงบรวมให้ ต้องเปิด Issue ให้ผู้จัดการโครงการ และคำขอต้องยังยื่นได้หลังผู้จัดการโครงการกรอกงบรวมเอง
22. เมื่อระบบเตรียมคำขอ re-baseline จาก Change Order ระบบต้องคัดลอก BCWS ของ baseline เวอร์ชันที่มีผลมาเป็นค่าตั้งต้น และต้องไม่ยอมให้ยื่นคำขอจนกว่าผู้จัดการโครงการจะกดยืนยันชุดค่านั้น

### การตัดสินใจที่ผู้ใช้ยืนยันแล้ว (2026-08-15)

ผู้เขียนตัดสินใจแทนในตอนแรกและผู้ใช้ยืนยันทั้งชุดแล้ว:

- **แบบก่อสร้างที่ cache ไว้ขณะออฟไลน์ — เปิดได้แต่ต้องเตือน** ไม่บล็อก เพราะการบล็อกทำให้ทำงานออฟไลน์ไม่ได้จริง ซึ่งขัดกับเหตุผลทั้งหมดที่มี FR-003-12 อยู่ (BR-003-04, FR-003-14)
- **ธง "เปิดเผยต่อลูกค้า" ใช้กับทั้ง `Issue` และ `Document`** ไม่ใช่เฉพาะ Issue เพราะเอกสารภายในมีปัญหาแบบเดียวกัน

#### เพิ่มเติมเมื่อ 2026-08-17

การตัดสินใจต่อไปนี้เกิดขึ้นเมื่อ 2026-08-16 ในรอบที่ผู้ใช้ไม่ได้ตอบคำถาม ผู้เขียนจึงเลือกตัวเลือกที่แนะนำไว้ก่อน และผู้ใช้ยืนยันทั้งชุดเมื่อ 2026-08-17:

- **FR ที่รองรับการระบุผู้จัดการโครงการ สิทธิ์ผู้บริหาร และสถานะโครงการ อยู่ในสเปคนี้ (FR-003-22, FR-003-23) ไม่ใช่ SPEC-002** — แม้คำสั่งเดิมจะให้ทำแบบเดียวกับ FR-002-18 แต่ FR-002-18 ใช้ได้เพราะสเปคนี้ยกช่องทางแจ้งเตือนให้ SPEC-002 เป็นผู้สร้างไว้ชัด ส่วนเรื่องสิทธิ์และ `Project` สเปคนี้ประกาศความเป็นเจ้าของไว้ตรงข้าม การลอกแบบมาตรง ๆ จะสร้างข้อขัดแย้งข้ามสเปคชนิดเดียวกับที่ audit เพิ่งแก้ไป
- **หลัก default-deny ใน FR-003-07 และ BR-003-01** — แจกแจงชนิดข้อมูลที่ห้ามเห็นไว้ครบ แล้วปิดท้ายว่าสิ่งที่ไม่อยู่ในรายการอนุญาตถือว่าปฏิเสธ เพื่อให้ค่าพยากรณ์ตัวใหม่ในอนาคตถูกปฏิเสธเองโดยไม่ต้องรอ audit จับ

### ข้อกำหนดจากเอกสารต้นทางที่ถูกปฏิเสธ พร้อมเหตุผล (2026-08-16)

เอกสาร "ระบบควบคุมงานก่อสร้างเพื่อความสำเร็จของโครงการ" มีข้อกำหนด 2 ข้อที่ขัดกับสิ่งที่สเปคนี้ตัดสินไปแล้ว บันทึกไว้เพื่อไม่ให้ถูกเสนอซ้ำ:

| ข้อกำหนด | ผลการชี้ขาด | เหตุผล |
| --- | --- | --- |
| **REQ-F09** ส่วน "คำนวณผลกระทบต่อเวลาและต้นทุนอัตโนมัติ" | **ปฏิเสธ** — กระบวนการสองขั้นตาม FR-003-15 และ BR-003-07 ยังบังคับใช้ครบ | ผลกระทบของ Change Order ก่อสร้างขึ้นกับหน้างานและ critical path ตัวเลขอัตโนมัติจะผิดบ่อย และผิดในทางที่ลูกค้าจำได้ว่า "ระบบบอกว่าเท่านี้" ซึ่งเป็นต้นทางของข้อพิพาทตอนวางบิลที่สเปคนี้ตั้งใจแก้ |
| **REQ-F11** คำนวณต้นทุน bottom-up จาก BOQ | **เลื่อน** — ไม่ตัดทิ้ง แต่ไปพร้อมกับการเปลี่ยนแกน BCWS ตาม BR-003-09 | REQ-F11 เป็นเรื่องของ*การประมาณราคา* ไม่ใช่*การวัดผล* การรับเข้ามาตอนนี้ขยายขอบเขตของรอบที่ยังไม่ได้เริ่มลงมือ และ `WBS_Task` เก็บงบต่องานไว้แล้วตาม FR-003-04 รอวันเปลี่ยนแกน |

ทางสายกลางที่พิจารณาแล้วยังทำไม่ได้ในรอบนี้: ให้ระบบคำนวณ **ตัวเลขตั้งต้น** ให้ผู้จัดการโครงการเห็นคนเดียวแล้วแก้ก่อนตอบลูกค้า — ทำไม่ได้เพราะต้องมีฐานต้นทุนต่องานจาก BOQ ซึ่งถูกเลื่อนไปพร้อมกัน ควรกลับมาพิจารณาพร้อม REQ-F11
